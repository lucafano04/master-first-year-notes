\section{Introduction to the course [10/09/2026]}
The objective of the course is to provide principles, techniques, and tools of Security Testing.

The project as part of the exam is written in Java, but the course also explores other programming languages like C/C++, Python, PHP, and SQL. This is because different programming languages have different vulnerabilities.
\subsection{Contents of the course}
Here are described the main topics of the course
\paragraph{Introduction to Security Testing} An overview of the security testing life-cycle, vulnerabilities, bugs and secure coding
\paragraph{Context} Than a context about Vulnerability analysis, rate and repositories will be given.
\paragraph{Vulnerabilities} A in detail presentation of SQL Ingection, XSS, String format and more 
\paragraph{Vulnerability detection} Both Static and Dynamic analysis will be discussed, and an overview of AI-based vulnerability detection will be overseen.
\paragraph{Tools} For those analysis tolls needs to be provvided, they will be analized and discussed.
\paragraph{[OPTIONAL] Advanced Topics} 

\subsection{Exam}
The exam is composed of two parts:
\begin{itemize}
    \item A written test with questions and exercises with both open and closed form questions (maximum two (2) hours) - About 60\% of the grade
    \item A written project report \textbf{to be submitted before the written exam} - About 40\% of the grade
\end{itemize}
Is permitted to attend both in one session or distinct sessions with no expiration date, both parts need to be at least 18/30, grades are expressed out of 30.

A simulation of the written part will be performed. Some laboratories will be devoted to work on the exam project.
\subsubsection{Project rules}
\begin{itemize}
    \item The groups can be composed by one or two students
    \item The project can be submitted maximum two non consecutive times
    \item It the project is graded by a fail two times than a different test have to be arranged
    \item A passing project can be used for a maximum of two written tests
    \item In case of passing final grade the project can not be resubmitted
    \item In case resubmission, a clear difference/delta between the first and the second submission must exists; otherwise the final score will be reduced of 1.
\end{itemize}

\section{Concepts, Notions, and Context [10-14/09/2026]}
We will start by giving the definition of Software and Security
\begin{definition}{Software}{software}
    A Software is composed by a set of Programs and Data witch provides functionalities. Often, it could be part of a cyber-physical system.
\end{definition}
\begin{definition}{Security}{security}
    Understanding and identifying software-induces security risks and how to manage them.
\end{definition}
With these definition we can conclude that the software plays a crucial role in providing security but it's one of the relevant \textbf{source of security issues} and problems. Meanwhile the relevance of security has been increasing but still not enaught. Indeed programming courses do not pay mutch attention to it and many developers have a lomited training in software security or no training at all, this is enhanced by the fact that the goal is still developing the software.
\paragraph{Why is software a source of security?}
Most developer produce \textbf{insecure code}. Some relevant factors are:
\begin{itemize}
    \item Limited Training
    \item Textbooks do not focus on security
    \item Limited security audits
    \item Dev. focus on feature implementation and not security
    \item Security is complex and expensive, requires time and resources
    \item Legacy software is often unsafe
\end{itemize}
Security is always considered a \textbf{secondary factor}, often is a \textbf{trade-off (or a conflict)} among: \textbf{Security}, \textbf{Functionality} and Convenience/Opportunities.
\begin{definition}{Secure Software}{secure_software}
    A software system is \textbf{secure if it satisfies specified security objection}.

    E.G., \textbf{Confidentiality}, \textbf{Integrity} and \textbf{Availability} requirements for the system's data and functionality.
\end{definition}
In general the \textbf{CIA} triad is not enough, there are other proprieties like: Authentication, Authorization, Privacy, Anonymity, Non-repudiation, Reliability, Audit, etc\dots\\
Security is about \textbf{preventing and imposing countermeasures to reduce risks} to relevant assets to acceptable levels.
\begin{concept}{Security Policy}{security_policy}
    A security policy specifies what security requirements and goals the countermeasures are intended to achieve.
\end{concept}
\begin{concept}{Security Mechanisms}{security_mechanisms}
    Security mechanisms and controls are applied to enforce the security policy as defined in \cref{cpt:security_policy}
\end{concept}
\begin{concept}{Security by Design}{sec_by_design}
    Security by Design referees when security is taken care of design the design, implementation, and testing phase (i.e. each phase) of software development
\end{concept}
A system is as secure as its weakest element, a system is composed by actors
\begin{description}
    \item[System] Provides data and services
    \item[Honest user] Uses the system as intended
    \item[Dishonest attacker] Attempts to find issues using unusual interaction and features to produce harmful effects. Like disrupting honest user's use (IA), learns information intended for honest user only (C) or intercepts communications (C).
    \item[Defender] Protects against possible attacks (known and un-known)
\end{description}
It's important to distinguish between safety and security
\begin{concept}{Safety vs Security}{safety_security}
    Safety is about protecting from accidental risks, security is about mitigating \textbf{risks of dangers caused be intentional, malicious actions}
\end{concept}
\begin{concept}{Security Software Failure}{sec_software_failure}
    A Security software failure is a scenario in witch the software dose not achive the security objectives/requirements. Software issues that can cause such failure exists.
\end{concept}
Most software has no clear and specific objectives, these are not absolute but often specific and case-dependent. Usually these are traded off against non-functional requirements. For this reason software design and implementation issues (e.g. bugs) can lead to a \textbf{substantial disruption of the software} and its behavior.

So \textbf{Security} it's a \textbf{System property, not a feture} and part of reliability.

\paragraph{Design and implementation Issues}
There are multiple kinds of implementation issues like: \textbf{Bugs in software, environment} like in architecture, infrastructure, components, etc, \textbf{inappropriate features} in the infrestructure or resued software (like libraries), \textbf{inappropriate} use of features provvided by the infrastructure or resued software. Possible causes of those are mainly: Unclear or missing requirements, Complexity of features, Time Pressure, characteristics of a programming language, Developer/Manager error.

\begin{definition}{Bug}{bug}
    The system isn't behaving as it's designed to behave
\end{definition}
\begin{definition}{Vulnerability}{vulnerability}
    A chain of \textbf{weakness} linked by casuality; it starts with a bug (\Cref{def:bug}) and ends with an error witch, if exploited, leads to a security failure (\Cref{cpt:sec_software_failure})
\end{definition}
Many security issues are related to vulnerabilities due to bugs, defects, or design flaws in a targeted software system.

\paragraph{Common Wakness Enumeration (CWE)}
CWE provides a publicly aviable list of the most common software (and hardware) weakness that can contribute to security vulnerabilities. Each CWE is described by several fields. Why is this done, if the needed function is in a package affected numbered by a CWE the weakness can be isolated and mitigated during the design of the application before the deploy. Also fixing a weakness before the vulnerability is introduces is a lot less pricey. 

\paragraph{Common Vulnerabilities and Exposures (CVE)}
CVE it is a publicly available list of entries that describes vulnerabilities in widely-used software components. Each CVE is described by several fields
